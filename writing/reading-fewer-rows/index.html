The only query optimisation that always works is reading less

Most slow queries are not slow because the engine is slow. They are slow because they read a year to answer a question about a week, and no amount of tuning fixes that.

In short

  • Most slow queries read far more data than the answer needs; no setting fixes that.
  • Name your columns, keep partition pruning by never wrapping the date column in a function.
  • Cluster on what you filter by, not what you group by, and filter before joining rather than after.
  • A bigger machine works once and the problem returns at the new size, with the invoice permanently larger.

Tuning almost always starts in the wrong place — at the settings, the machine, the engine — and almost always ends in the same place: something was reading far more data than the answer needed.

Everything below is a way of reading less. There is no sixth idea, and there is no setting that makes reading a hundred gigabytes fast.

Read fewer columns

On a columnar store — which is what every analytical warehouse is — select * is not a convenience, it is a bill. The engine reads only the columns you name, so naming all of them costs exactly as much as it sounds like it should.

Read fewer partitions

A partitioned table is split into pieces by some column — nearly always a date. If the query says which piece it wants, the engine never opens the others.

-- Reads every partition: the function hides the column from the planner
where date_trunc('day', created_at) = '2026-05-01'

-- Reads one: the column is compared directly to a constant range
where created_at >= '2026-05-01' and created_at < '2026-05-02'

Wrapping the partition column in a function is the single most common way people lose partition pruning without noticing. The query is still correct, still returns the same rows, and now reads the whole table. Nothing warns you.

Read fewer blocks within a partition

Clustering — sorting the data physically by a column you filter on — lets the engine skip blocks inside a partition. It is the cheapest big win available, because it changes nothing about how the data is queried.

Cluster on what you filter by, not on what you group by. That is the mistake I keep seeing: a table clustered on the reporting dimension, filtered by customer, skipping nothing.

Read fewer rows before the join

Joins multiply. Filtering after a join means the engine built rows it was about to throw away.

  1. Filter first

    Push every condition as close to the source table as it will go. Modern planners do a lot of this for you, and they stop being able to as soon as the query gets complicated enough for it to matter.

  2. Aggregate before joining, where you can

    Joining two tables of a million rows to then count them is a very expensive way to count.

  3. Watch for the join that fans out

    One duplicate key on the wrong side turns a million rows into ten million and every number after it is wrong as well as slow.

Do not read it again

The fastest scan is the one that already happened yesterday and was written down.

If a dashboard asks the same question every morning, answer it once at night and store the answer. This is unfashionable, extremely effective, and the reason those nightly summary tables you keep meeting still exist.

The order to try things

StepEffortTypical effect
Name the columnsminutesLarge on a column store
Fix the date filterminutesLarge, if pruning was lost
Cluster on the filter columnhoursLarge and permanent
Rewrite the joinsdaysSometimes large
Precompute the answerdaysTotal, and it never regresses
Bigger machinea phone callLinear, and it comes back next quarter

The last row is worth stating plainly because it is what usually gets tried first. It works, once, and the problem returns at the new size — with the invoice permanently larger.

Questions

Why did my query get slower after I added a date filter?

Almost always because the filter wraps the partition column in a function, which hides it from the planner. The query stays correct and quietly reads every partition. Compare the column directly against a range instead, and nothing will warn you if you do not.

Should I cluster on the column I group by?

No — cluster on what you filter by. Clustering lets the engine skip blocks it does not need to open, and it can only skip based on the filter. Clustering on a reporting dimension is the most common way to do this work and gain nothing.

Is a bigger machine ever the right answer?

Sometimes, as a deliberate stopgap while you fix the query. It works once, the problem returns at the new size, and the invoice stays larger permanently. Treat it as buying time rather than as a fix, and write down what you bought the time for.

Will adding an index fix this?

On a row store, often yes — an index is precisely a way to read fewer rows. On a columnar warehouse there are usually no indexes at all, and partitioning and clustering do that job instead. Knowing which kind of store you are on decides which half of this advice applies.

How do I find out what a query really read?

Every engine will tell you: the execution plan, plus the bytes or rows scanned. Read that number before and after each change, because it is the thing you are actually optimising. Wall-clock time moves for reasons that have nothing to do with your query.
