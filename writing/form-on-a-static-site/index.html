A form on a static site needs one Worker and nothing else

A static site cannot receive a POST. Everything else about adding a contact form is downstream of that one sentence — and the whole answer fits on a screen.

In short

  • A static site cannot receive a POST, so a contact form needs exactly one function that can.
  • Roughly forty lines of edge function: validate the fields, drop the obvious spam, forward the rest.
  • Answer with a redirect rather than JSON, so the form still works without JavaScript.
  • Keep the destination address in a secret on the function — never in the page, where anyone can read it.

A static site is a pile of files. Files cannot receive a form submission, so the moment you want a contact form you need exactly one thing that can — and it is worth keeping that one thing as small as it sounds.

The usual reaction is to reach for a form service. That works, and it also means a third party holds your messages, shows a logo, rate-limits you, and eventually changes its pricing. The alternative is about forty lines.

The shape

The Worker

export default {
  async fetch(request, env) {
    if (request.method !== 'POST') {
      return new Response('Method not allowed', { status: 405 })
    }

    const form = await request.formData()
    const email = String(form.get('email') ?? '').trim()
    const message = String(form.get('message') ?? '').trim()

    // Validate here, not in the browser. Browser-side validation is a courtesy to the
    // person filling the form; it is not a control, because nothing stops a POST arriving
    // from somewhere that never loaded your page.
    if (!email.includes('@') || message.length < 10 || message.length > 5000) {
      return new Response('Bad request', { status: 400 })
    }

    // A hidden field that a person never sees and a naive bot always fills in.
    if (form.get('company')) {
      return new Response('OK', { status: 200 })   // lie politely
    }

    await fetch(env.SINK_URL, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ email, message, at: new Date().toISOString() }),
    })

    return Response.redirect(new URL('/thanks', request.url), 303)
  },
}

That is the whole backend.

env.SINK_URL is a secret set on the Worker, never written in the repository. It is also the reason the Worker exists at all rather than the form posting directly to whatever is storing the messages: the address of that thing stays private, and the Worker is the only place that knows it.

Why not post straight to the store

Three reasons, and only the first is obvious.

  1. The address stays secret

    Anything the browser can see, anyone can see. Post directly and the endpoint is public forever, whatever you do afterwards.

  2. You get somewhere to put the rules

    Length limits, a honeypot field, a rate limit per address, a blocklist. All of it belongs in one place you control, and none of it can live in a static file.

  3. You can change what is behind it

    Today a spreadsheet, tomorrow a database, next year an inbox. The form never changes, because the form only ever knew about the Worker.

The part everybody gets wrong

Return a redirect, not JSON. If the form is a plain HTML form and the response is a 303 to a thank-you page, the whole thing works with JavaScript disabled, on an old phone, and in a text browser. Answer with JSON and you have quietly made JavaScript a requirement for someone to contact you.

Add the JavaScript afterwards if you want it to submit without a page load. Written in that order the fallback is real. Written the other way round, the fallback never gets built.

What it costs

Nothing, in practice, at the volumes a personal site or a small company sees. The free allowance on every edge platform is measured in tens of thousands of requests a day, and a contact form that gets fourteen a week is not going to trouble it.

The real cost is that you now own forty lines of code. That is the trade, and for a form it is a good one.

Questions

Why not just use a form service?

It works and it is faster to set up. In exchange a third party holds your messages, shows its branding, sets your rate limits and changes its pricing without asking. For roughly forty lines you keep all of that, and the messages go wherever you want.

Will this stop spam?

It stops the cheap kind. A hidden field that only a bot fills in, a minimum message length and a per-address rate limit remove most automated noise. A determined human is a different problem, and no form handler solves that one.

Does the visitor need JavaScript?

Not if the function answers with a redirect to a thank-you page, which is why it does. Plain HTML forms have worked for thirty years; adding JavaScript afterwards is an enhancement. Build it the other way round and the fallback never actually gets written.

Where should the messages actually go?

Wherever you will read them. A spreadsheet works and is easy to share; a mailbox works and needs no login; a database is right once you need to search them. The function hides that choice, so changing your mind later costs one deployment and no edit to the form.

Do I need a CAPTCHA?

Start without one. A hidden field, a length limit and a rate limit stop most automated submissions, and a CAPTCHA taxes every honest visitor to stop the rest. Add one only when the logs show you genuinely need it, and prefer the kind that does not make people label traffic lights.
