Google Apps Script is a worse backend than you want and a better one than you think

It has no dependency management, no real editor and a hard execution limit. It also gives you a database, an authenticated mail sender and a scheduler for nothing, already connected to each other.

In short

  • Apps Script gives you a store, an authenticated mail sender, a scheduler and an identity with no keys to manage.
  • It costs you dependency management, a hard runtime limit per execution, and quotas that stop public use.
  • Right for internal tools at human pace where the data already lives in a spreadsheet.
  • Put an edge function in front of it: the script URL stays private and validation happens before quota is spent.

Nobody chooses Apps Script. You end up with it, usually because the data was already in a spreadsheet and somebody needed a form to write to it. Having ended up there several times, I have stopped being embarrassed about it — but only for a specific shape of problem.

What you actually get

A spreadsheet is a passable database for small, human-scale data: it is already backed up, already shared with the right people, already has an interface your colleagues can use without being taught, and already has an audit trail. Those are five things that cost real work to build.

Store
a spreadsheet, with revision history and sharing
Mail
authenticated sending from a real address, no provider to configure
Schedule
time-driven triggers, built in
Endpoint
publishable as a web app with doGet and doPost
Identity
runs as you, with your access, with no keys to manage

That last line is the one that matters and the one nobody mentions. Doing the same thing properly means a service account, a key file, a secret store and a rotation policy — four things that can be got wrong. Here there are none, because the script is you.

What it takes away

  1. No dependency management worth the name

    You are writing against what the platform provides. Pulling in a library is awkward and upgrading one is worse.

  2. A hard limit on how long a run may take

    Anything slow has to be written to stop cleanly, record where it got to, and be picked up by the next run. That is a real pattern to learn, not a footnote.

  3. Quotas that are generous until they are not

    Mail per day, script runtime per day, calls per minute. Fine for an office, a wall for anything public. Check the current numbers before you design against them; they move.

  4. Version control is bolted on

    There is tooling to keep the source in git and it is the first thing to set up. Editing production code in a browser tab is exactly as bad as it sounds.

The pattern that makes it usable

Do not expose the script to the internet. Put an edge function in front of it.

Published Apps Script web apps answer with redirects, which makes cross-origin requests from a browser genuinely painful. Calling the script server to server — from a Worker — sidesteps that entirely, and is another reason the gateway is not just about secrecy.

When it is the right answer

SituationVerdict
Data already lives in a spreadsheet people editYes — do not migrate it to feel professional
Internal tool, tens of users, human-pacedYes
Sending mail as a real person from a real addressYes, and it is genuinely hard elsewhere
Public endpoint at any volumeNo — the quotas will decide for you
Anything you will still be extending in three yearsNo — the missing tooling compounds

The question is not whether it is a serious platform. It is whether the thing you are building will ever need one.

Most small internal tools never do. The ones that do usually announce it clearly — a quota you keep hitting, a run that will not fit in the time limit — and by then you know enough about the problem to rebuild it properly in a fortnight.

Questions

Is Apps Script safe to expose to the internet?

Not directly. Put an edge function in front of it: the script's address stays private, validation and rate limiting happen before any quota is spent, and you avoid the awkward cross-origin behaviour of published web apps. Calling it server to server sidesteps that entirely.

What are the real limits?

A per-execution runtime cap of a few minutes, plus daily quotas on mail and total script runtime. The exact numbers differ by account type and change over time, so check the current figures before designing against them rather than trusting any article, including this one.

When should I move off it?

When you keep hitting a quota, when a job will not fit inside the execution limit, or when you are still extending the thing in a year. Any of those three is the platform telling you the problem outgrew it, and by then you understand the problem well enough to rebuild it quickly.

Can I keep the code in version control?

Yes, and it is the first thing to set up. Google's command-line tool pushes and pulls the project so the source lives in git like anything else. Editing production code in a browser tab, with no history and no review, is exactly as bad as it sounds.

Is it slow?

Slower than a proper runtime, and rarely slow enough to matter for the work it suits. Reading a few hundred spreadsheet rows takes a moment; reading tens of thousands one at a time is painful. Batch your reads and writes and most of the complaints about speed disappear.
