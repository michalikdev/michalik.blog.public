What a queue gets you that a scheduled job never will

A job that runs every hour hides its failures for an hour, overlaps with itself under load, and cannot tell you which item is stuck. A queue is barely more code.

In short

  • A scheduled job fails quietly in three ways: it overlaps itself, silently skips, or hides a single stuck item.
  • A queue is one table and one query — the whole trick is `for update skip locked`.
  • What you gain is per-item state: what is stuck, how far behind you are, and retrying one record instead of all of them.
  • Keep the timer. Its job becomes putting work into the queue rather than doing the work.

The scheduled job is the first thing everybody reaches for, and it is right often enough to be a habit. The habit survives well past the point where it stops being right, because the failure it produces is invisible.

The three ways it fails quietly

  1. It overlaps with itself

    The job takes longer than its interval, so a second copy starts while the first is running. Now two of them are working on the same rows. Whether that is harmless or catastrophic depends on code that was written assuming it could never happen.

  2. Or it skips, silently

    The other common guard is a lock file: if the previous run is still going, do nothing. That is safer and it means a slow run swallows the next one, with nothing anywhere saying so.

  3. It has no idea what is in it

    A scheduled job knows the time. It does not know that one particular item has failed on eleven consecutive runs, because it has no concept of an item at all.

The third one is the expensive failure. Everything looks healthy — the job runs, exits zero, logs nothing alarming — and one record has been silently failing since March.

What a queue is, minimally

Not a message broker. Not infrastructure. A table:

create table work (
  id          bigserial primary key,
  kind        text        not null,
  payload     jsonb       not null,
  state       text        not null default 'ready',   -- ready | running | done | failed
  attempts    int         not null default 0,
  run_after   timestamptz not null default now(),
  last_error  text,
  updated_at  timestamptz not null default now()
);

And one query that takes the next item without two workers taking the same one:

update work set state = 'running', attempts = attempts + 1, updated_at = now()
where id = (
  select id from work
  where state = 'ready' and run_after <= now()
  order by run_after
  for update skip locked          -- the whole trick is on this line
  limit 1
)
returning *;

for update skip locked is what makes this safe with several workers: each one takes a row nobody else has locked, rather than queueing behind the same row. It has been in PostgreSQL since 9.5 and it removes the only genuinely hard part of writing a queue.

The retry column is the one that changes daily life. With a scheduled job, fixing one bad record means running the whole batch again and hoping the rest is idempotent. With a queue it is one update.

A scheduled job knows what time it is. A queue knows what is wrong.

Keep the schedule

None of this removes the timer — something still has to wake up and put work into the queue, and a scheduled job is the right tool for exactly that. The change is what it does when it wakes: it enqueues, and something else does the work.

That split is the whole idea, and it is why this is a small change rather than a migration.

Questions

Do I need a message broker for this?

No. A table with a state column and one query using `for update skip locked` gives you safe concurrent workers, retries and per-item visibility. A broker earns its place at volumes and durability guarantees most internal systems never reach.

What stops two workers taking the same job?

`for update skip locked` in the claiming query. Each worker locks a row nobody else has locked instead of queueing behind the same one. It has been in PostgreSQL since 9.5 and it removes the only genuinely hard part of writing a queue.

Do I still need a scheduled job?

Yes, and that is the point. Something has to wake up and put work into the queue, and a timer is exactly right for that. What changes is that it enqueues rather than does the work, so a slow item no longer blocks the next run.

How do I stop an item retrying forever?

Cap the attempts and move the row to a failed state when it is exceeded. Then the important half: something has to look at that state. A failed queue nobody reads is the same silence you left the scheduled job to escape, only with better bookkeeping.

Where do the workers run?

Anywhere that can reach the database. A long-running process, a container, or a scheduled job that drains the queue for a minute and exits — all three work, because the queue holds the state rather than the worker. That is what makes them replaceable without anything being lost.
