Every element on this site, and when to use each one

The whole vocabulary an article here can use — rendered, with the markup that produced it, and with the case against each one where there is a case.

In short

  • Write plain HTML with known classes. There is no syntax to learn and nothing to import.
  • Every widget is a real element — an aside, an ordered list, a description list, a figure — so the page still works read aloud or printed.
  • Two things have logic in them and are therefore components: the chart and the console replay. Everything else is CSS.
  • Most of the entries below carry a warning about when NOT to use them. Those are the useful half.

Every element an article on this site can use, rendered here next to the markup that produced it. It is a reference, and it is also an argument: about half of what follows is about when not to reach for a thing.

Ordinary markdown needs none of this and produces a perfectly good article on its own — headings, lists, quotes, code, links, bold, italic, inline code. The classes below exist for the handful of things markdown has no way of saying, and an article that uses none of them is not a lesser article.

Everything on this page follows the direction chosen with the A/B/C/D control at the top. Nothing in the article styles names a colour — they all read the direction's own tokens — so every element here changes with it, the chart and the console included.

How an entry is written

Four conventions before any markup at all. Every one of them exists for a reader first; written the other way round they turn into keyword mush, which is the single thing Google's guidance is unambiguous about.

  1. A short answer at the top

    Three or four lines, sixty to eighty words, in the entry's front matter. Written for the reader who will not read the article — and there are more of them than of the other kind. If they leave after it, they should still have got something true.

  2. Answer the heading in the first paragraph under it

    Forty to sixty words, directly, before any build-up. A section called "What it takes away" opens by taking something away.

  3. Second-level headings for sections, third for parts of one, nothing deeper

    The contents list is built from these, so a heading used for emphasis rather than structure shows up as a lie in the navigation.

  4. Four to six real questions at the end

    Below four it reads as an afterthought; above six the article itself failed and is apologising in instalments.

What is deliberately not done: no llms.txt, no separate markdown copies of pages, no chopping content into blocks for machines. Google says plainly that none of it is needed, and every one of them is a second copy of the truth to keep in step with the first.

Opening paragraph

The one paragraph that decides whether anyone reads the rest. One per article — a second one is not an opening, it is just large text.

Most slow queries are not slow because the engine is slow. They are slow because they read far more data than the answer needed.

Notes

Three tones, and no more. Every extra tone makes the previous ones mean less.

The plain one. For something worth stepping out of the flow for.

For something that will cost you if you skip it.

For the thing that finally worked.

<aside class="note"><p>…</p></aside>
<aside class="note note--warn"><p>…</p></aside>
<aside class="note note--good"><p>…</p></aside>

The label — Note, Watch out, What worked — is written by the stylesheet, so it can never say "warning" on a note that stopped being one.

Steps

  1. Stop the service first

    Otherwise the next step races it, and you get a backup of a half-written state.

  2. Take the backup

    And read the size. A backup that is suspiciously small is the only warning you will get.

  3. Start it again

    Then check the log rather than the process list — a service can be running and useless. 
<ol class="steps">
  <li><h4>Stop the service first</h4><p>Otherwise the next step races it.</p></li>
  <li><h4>Take the backup</h4><p>And read the size.</p></li>
</ol>

A real <ol>, so the numbers stay correct when you insert a step in the middle at two in the morning.

Terminal

$ nvidia-smi --query-gpu=memory.used,memory.total --format=csv
memory.used [MiB], memory.total [MiB]
17224 MiB, 24576 MiB

<pre class="terminal"><code>$ nvidia-smi --query-gpu=memory.used --format=csv
17224 MiB
</code></pre>

The $ is part of the text on purpose: someone copying the block gets what was actually typed. For a program rather than a transcript, use an ordinary fenced code block — that one gets syntax colouring, this one does not.

A grid of identical cards is what a page looks like when nobody decided what mattered. Every card the same size says every item is equally important, which is almost never true. Reaching for cards to break up a long article means the article needs headings.

A session, played back

::replay
---
title: npm run publish
lines:
  - "$ npm run publish"
  - "  ✔ 193 files"
---
::

The transcript is in the page from the start — selectable, searchable with the browser's own find, readable aloud, printable. None of which a screen recording is.

The replay is a button somebody presses. It never starts by itself: text that rewrites itself while a screen reader is reading it is hostile, and someone who came to copy one command should not have to sit through a performance first. With reduced motion requested, the button is not shown at all — a control that deliberately does nothing is worse than no control.

Pictures, side by side

<div class="gallery">
  <figure><img src="a.png" alt="What it shows"><figcaption>What to look at</figcaption></figure>
  <figure><img src="b.png" alt="What it shows"><figcaption>And here</figcaption></figure>
</div>

alt is not optional. A picture with no alternative text is invisible to a screen reader and to a search engine — which is to say invisible to everyone who cannot see it.

Questions

Do I have to use any of this?

No. Ordinary markdown produces a perfectly good article on its own — headings, lists, quotes, code, links. Everything here is for the handful of things markdown has no way of saying, and an article that uses none of it is not a lesser article.

Why classes instead of components?

A component is a file to maintain, a name to remember and a thing that can fail to import, in exchange for what a class and some CSS already do. It also matters in five years: this markup stays a valid document anywhere, rather than a page of dead custom tags.

Can I add my own?

Yes, and the bar is deliberately high. A new class earns its place by doing something the existing ones cannot, and by being a real HTML element rather than a styled div. If it is a variation on a note, make it a note.

Will these look right in the other visual directions?

Yes. Nothing in the article styles names a colour; everything reads the direction's own tokens. Switch with the A/B/C/D control at the top and every element on this page follows, including the chart and the console.

What breaks if I write HTML by hand?

One thing worth knowing: the markdown processor strips paragraph tags inside a list item, so what reaches the browser is a bare text node. The styles are written to survive that, but do not build anything that depends on that paragraph existing.
